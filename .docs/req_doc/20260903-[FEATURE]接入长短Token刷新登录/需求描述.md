# 需求描述：接入长短 Token 刷新登录

> 安全提示：本文不得记录真实账号、密码、Token、Cookie、Session ID、请求响应正文或生产内部地址。

## 任务属性

- 级别：L3（认证凭据、公共认证行为与兼容协议变化）
- 类型：FEATURE / SECURITY
- 任务状态：已完成（本地）
- 执行授权：已授权
- 授权来源：用户要求登录命令提供登录方式选择，并将 `mbs refresh` 改为调用 `/token/exchange/compat-session`
- 交付状态：本地实现与验证已完成，未发布、未真实网关联调

## 背景与演进关系

认证中心已增加登录型 Refresh Token、短期 Access Token 与兼容 Spring Session 桥。账号密码登录和扫码会话绑定成功后通过 `HttpOnly` Cookie 签发 `AUTH_REFRESH`；兼容交换以该 Cookie 为唯一长期凭据，旋转 Refresh Cookie、返回短期 Access Token，并建立或续接 `SESSION`。

本任务补充并部分修正 `20260902-[SECURITY]禁止持久化MBS_KEY`：`MBS_KEY` 禁令保持不变；原“Cookie 失效后必须重新登录”的本地待发布实现，改为只使用认证中心正式签发的登录型 Refresh Cookie 刷新。该变化尚未发布，不改变目标环境当前事实。

## 业务与安全边界

本任务包含：

1. 裸执行 `mbs login` 时以终端选择列表询问扫码登录、账号密码登录或后台长期 Refresh Token 登录；既有 `--password` 保留为显式快捷方式。
2. 扫码和账号密码登录只接收认证中心签发的 `SESSION` 与 `AUTH_REFRESH` Cookie；三种方式都不得观察、读取或保存 `MBS_KEY`。
3. 本地缓存允许保存标准化的 `SESSION`、安全用户摘要，以及二选一的“`AUTH_REFRESH` + Refresh 到期时间”或管理型 `LongToken`；文件继续使用仅当前用户可读写的权限。
4. 登录型 Refresh Cookie 调用兼容交换时只携带 Cookie；后台长期 Refresh Token 按认证中心管理型 `LongToken` 契约，通过 `Authorization: LongToken <token>` 调用同一入口。两种来源不得同时提交，且都不携带 Bearer。
5. 后台长期 Refresh Token 由用户通过隐藏终端输入手动粘贴，不提供命令参数或环境变量入口；登录成功后与兼容 `SESSION` 一同保存在仅当前用户可读写的认证缓存，后续 `mbs refresh` 自动使用且管理型 Token 本身不轮换。
6. Access Token 只保存在当前进程内存，不写入文件、环境变量、日志、stdout、遥测或命令参数。
7. 普通业务请求首次认证失败时最多交换并重试一次；重试同时采用内存 Bearer 和新 Cookie。
8. 认证拒绝或交换响应不符合契约时清除不可再安全使用的本地认证；暂时性网络失败不得伪装成功。
9. 每次执行 `mbs login`（包括重新登录或切换用户）时，必须在选择登录方式或收集新凭据前删除本地认证缓存；清理范围同时覆盖 `SESSION`、`AUTH_REFRESH`、管理型 `LongToken` 和安全用户摘要。

本任务不包含：

- 管理型 `LongToken` 的签发、回显、轮换或撤销；
- 修改认证中心、网关、业务服务、Docker 部署或生产配置；
- 使用真实账号、密码、Token 或 Cookie 自动联调；
- Git 提交、推送、发布或外部写入。

## 接口契约

- 登录：`POST /gateway/auth-center-service/auth/user/login/password` 或现有扫码绑定流程。
- 刷新：`POST /gateway/auth-center-service/auth/token/exchange/compat-session`，请求体为空；登录型凭据使用有效 `AUTH_REFRESH` Cookie，管理型凭据使用唯一 `Authorization: LongToken <token>` 头。
- 成功响应：业务码 `200`，`data.accessToken` 为无空白短字符串，`data.tokenType` 固定为 `Bearer`，`data.expiresInSeconds` 为正安全整数。
- 成功 Cookie：登录型 Refresh 分支必须取得旋转后的 `AUTH_REFRESH`；管理型分支不得下发 `AUTH_REFRESH`。两分支在 `SESSION` 未重新下发时可继续使用请求中既有 `SESSION`，新下发时必须替换；管理型首次交换必须取得 `SESSION`。
- Refresh Cookie 到期：优先使用服务端 `Max-Age`；扫码浏览器 Cookie 使用浏览器提供的绝对到期时间。

## 验收标准

1. 裸 `mbs login` 显示可键盘选择的三种登录方式，选择账号密码或后台长期 Refresh Token 时不启动浏览器；`--password` 兼容行为保持。
2. 密码登录和扫码登录都要求并保存 `SESSION`、`AUTH_REFRESH` 与有效 Refresh 到期时间。
3. 缓存读取拒绝重复 Cookie、控制字符、缺少 Refresh 到期时间、已到期或未来时间异常；旧 SESSION-only 缓存只在原两小时兼容窗口内可用，但不能刷新。
4. 后台长期 Refresh Token 只从隐藏终端输入取得，格式不合法时不发请求；成功交换后缓存 Token 与兼容 `SESSION`，缓存不得同时包含 `AUTH_REFRESH`。
5. `mbs refresh` 按缓存凭据类型正确调用兼容交换：登录型 Cookie 保存轮换值，管理型 Token 保持不变并更新兼容 `SESSION`；缺少或失效长期凭据时退出码为 2。
6. Access Token 不持久化、不输出；API 首次 401 后的唯一重试携带 `Authorization: Bearer` 和更新后的 Cookie。
7. 交换端点自身不进入业务客户端递归刷新；认证失败、网络失败、畸形响应和写缓存失败均有测试。
8. 定向测试、受影响模块测试、全仓测试、构建、命令帮助、安全扫描和差异检查通过。
9. `mbs login` 在任何登录选择、账号输入、密码输入、长期 Token 输入或浏览器启动前调用完整认证缓存清理；后续登录失败或取消时不恢复旧凭据。
