# 需求描述：修复登录完成与请求认证

> 安全提示：本文不得记录真实账号、密码、Token、Cookie、Session ID、请求响应正文、生产地址或未脱敏日志。

## 任务属性

- 级别：L3（认证、长期凭据、兼容 Session 与跨仓库调查）
- 类型：BUG / SECURITY
- 记忆键：`AUTH-CREDENTIAL-BOUNDARY`
- 任务状态：待验收
- 执行授权：已授权
- 授权来源：用户要求排查并修复扫码登录完成状态，以及账号密码/Token 登录后的业务请求未登录问题；必要时检查 `auth-center-service`
- 交付状态：待发布

## 故障现象

1. 用户完成扫码后，登录浏览器页面没有关闭，CLI 也没有输出登录成功提示。
2. 账号密码或管理型长期 Token 登录后，请求业务接口仍返回未登录；需要确认业务请求是否携带可用的短期 Bearer 或兼容 `SESSION`，以及认证中心签发/桥接接口是否满足客户端契约。

## 根因分析

问题由三组独立缺陷叠加，并非 CLI 普通业务请求漏带认证材料：

1. CLI 扫码仍打开旧商城 JSP，而当前缓存契约要求认证中心的 `SESSION + AUTH_REFRESH`。旧页面不会履行该契约，因此 Cookie 轮询一直等待，浏览器关闭与成功输出都不会执行。
2. 项目默认目标暂时使用远程 HTTP，长期 Refresh 不应经过明文扫码回调，且浏览器也不会保存 `Secure` Cookie。原页面又依赖安全上下文中的 `window.crypto.randomUUID()`；仅切换地址仍无法形成可用闭环。修复后认证中心在 HTTP 扫码回调中完全不创建 Refresh，CLI 只接受经身份验证的有界 Session-only。
3. 密码和管理型 LongToken 登录后，CLI 首个业务请求实际携带规范化 `SESSION` 与 `client-type: cli`；收到 HTTP 401 或业务码 601 后，唯一一次重试也会携带新 `SESSION` 与进程内 Bearer。真正的阻断是网关把认证中心的 HTTP 401 与依赖异常一并折成 `false`，最终回给 CLI 403；CLI 正确地不会对真实 403 刷新。网关负向权限缓存还使用滑动续期，可能持续遮蔽新的登录状态。
4. 真实 HTTP 扫码入口在返回二维码 HTML 时，旧认证拦截器会先调用 `request.getSession()` 并下发匿名 `SESSION`。CLI 原 HTTP 降级分支将首个单一 Session 立即交给 current-user，收到未认证后直接关闭浏览器，形成“还未扫码页面就闪退”。修复后 CLI 忽略已拒绝的匿名候选并等待回调旋转 Session，认证中心页面入口同时清理预登录 Session。

扫码调查同时发现原 `traceId → authenticated sessionId` 轮询可由另一浏览器领取认证 Session，且 OAuth state 未绑定发起浏览器。该路径不能作为修复基础，必须在启用新扫码页时一起停用。

## 业务与安全边界

本任务包含：

1. 为两项用户可见故障建立快速、确定、可无人值守运行的回归反馈环。
2. 修复扫码登录 URL 前置校验、页面错误快速失败、Cookie origin 隔离、底层可取消总超时、浏览器关闭、成功输出和认证缓存写入顺序。
3. 核对账号密码与管理型 LongToken 登录产物、缓存读取、compat-session 交换、业务请求 Cookie/Bearer 组装及唯一一次 401 重试。
4. 修复认证中心可打包扫码页、五分钟 HMAC state、HTTPS `__Host-` Cookie、同浏览器 Session、HTTP/HTTPS Refresh 分流和安全异常响应；停用跨浏览器 trace 会话领取。
5. 修复网关 401/403 分类和权限缓存语义：只缓存固定十秒的正向允许，历史负缓存重查，拒绝不缓存；为认证中心服务名和校验路径提供仓库契约默认值。
6. 同步必要测试、方法文档、任务审计与认证主题记忆。

本任务不包含：

- 读取、重放或记录任何真实凭据和生产响应；
- 改变 `MBS_KEY` 禁令、Access Token 仅内存、两类长期凭据互斥等既有安全边界；
- 修改普通业务接口语义、RBAC 权限、数据库数据、远程 Nacos/Redis 或部署环境；
- Git 暂存、提交、推送、发布或部署；
- 覆盖 `technical-center` 中既有的 `RbacService.java` 与 `graphify-out/` 用户修改。

## 输入与输出

- 输入：使用人工构造 Cookie/Token/响应的自动化场景；必要时使用本地 mock HTTP 服务模拟跨请求认证链路。
- 输出：HTTPS 扫码取得唯一 `SESSION + AUTH_REFRESH` 后验证身份、保存、关闭浏览器并输出一次成功；远程 HTTP 只在唯一 SESSION 通过 current-user 验证后保存最长两小时并警告不可刷新。
- 输出：密码或 Token 登录后的业务请求携带正确且最小的认证材料；认证中心 401 经网关保留，使客户端按既有规则交换并最多重试一次，真实 RBAC 拒绝仍为 403。
- 输出：认证中心以限时 HMAC state 和当前协议短期 Cookie 绑定同一浏览器；HTTPS 使用浏览器强制 host-only 的 `__Host-` 名称，HTTP 明确保留受限兼容。旧会话转移端点固定 410；认证请求异常日志不记录 Header、Cookie、query 或 body。

## 验收标准

1. 回归测试能在修复前稳定命中旧扫码入口、HTTP 长期凭据断链、未防伪 state、trace 会话转移和网关 401→403，修复后对应场景通过。
2. 扫码成功后认证缓存只保存允许字段，浏览器关闭动作和成功输出均只发生一次；HTTPS 不降级，HTTP 的 SESSION-only 必须先验证身份且最长两小时；非法 URL、页面 5xx、绝对超时、非法/重复 Cookie、用户查询失败仍失败关闭。
3. 密码/LongToken 登录产物、缓存到请求的 Session 归一化和 Node 实际请求线分段证明业务首发传递 `SESSION`；首次认证失败时，compat-session 的 Access Token 和新 `SESSION` 同时应用于唯一重试，连续 401 不超过两次请求。
4. 普通业务请求不携带 `AUTH_REFRESH` 或管理型 `LongToken`，Access Token 不持久化、不输出。
5. 认证中心测试覆盖页面资源打包、HMAC state/时效、HTTP/HTTPS Cookie、成功 Session、HTTPS Refresh、HTTP 无 Refresh、失败清除和旧端点 410；网关测试覆盖默认配置、401、403、5xx、固定正缓存、历史负缓存重查和拒绝不缓存。
6. CLI 定向测试、全仓 297 项、14 包构建、认证中心 113 项及打包、网关 21 项及打包、JAR 资源/SDK 和差异/敏感信息检查通过。
7. 未使用真实凭据或目标环境进行验证时必须明确披露，不能宣称已完成真实联调、发布或部署。
