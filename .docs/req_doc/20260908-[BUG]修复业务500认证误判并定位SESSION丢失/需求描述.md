## 故障现象

登录后执行热销商品列表命令，后端稳定返回业务 `code=500`，CLI 又将该响应解释成认证失败并退出。用户在直连 auth-center 时观察到请求 Cookie 和响应 `Set-Cookie` 中的 SESSION 不同，怀疑存在多个冲突会话。

## 已确认事实

1. 原命令及最小参数命令都稳定得到 HTTP 200、业务 `code=500`、空业务说明。
2. 当前 CLI 实际只发送一个缓存 SESSION；无重复 Cookie、无重定向。
3. 同一 SESSION 调用 current-user 可被 auth-center 识别；随后调用 compat-session 成功复用该会话，因此响应不发送 `Set-Cookie` 是正常行为，不是 Axios 漏读或网关丢头。
4. 截图中的“请求旧 SESSION、响应新 SESSION”表示 auth-center 在请求会话无用户或用户不匹配时进行安全轮换。响应值是后续权威值，不代表两个会话都应继续使用。
5. 同一个已被 auth-center 识别的 SESSION 在远程 ERP 热销列表链路中仍表现为缺少 `sysloginadmin`。当前 dev Nacos 未发现 `erpmonitor` 服务，网关 `ServiceRouteFilter` 因而必走非本机 `legacyNginxUri` 回退；原命令不会访问本机已启动的 10102，也没有形成完整本地三服务链路。
6. 本地 auth-center 与 erp-monitor 的 Spring Session Redis endpoint、DB 0、namespace、Cookie 名、JDK 序列化方式及 `DbSysadmin` 序列 UID 一致，已排除这些源码/本地配置层不兼容。
7. `HotProductMonitor.hotProductAllListing()` 未检查 Session 用户，便在自身 try/catch 之外解引用空 `DbSysadmin`；Java 8 下由全局异常处理映射成当前看到的空说明 500。
8. CLI 将全部业务 `code=500` 映射为 `NotAuthenticatedError`，会无意义地执行一次凭据交换和一次业务重试，并把普通 API 错误报告成认证退出码 2。
9. api-gateway 的全局 CORS 过滤器会对同一 exchange 调用两次剩余过滤链。Spring Cloud Gateway 的 already-routed 标记通常阻止第二次真实 HTTP 转发，且该过滤器不删除 `Set-Cookie`；这是独立缺陷，不是当前 SESSION 故障的已证实根因。

## 根因与责任边界

已确定并已修复两个直接代码问题：

- `mbs-cli`：普通业务 500 被误判成登录失效，放大了服务端故障。
- `erp-monitor`：缺少登录用户时发生未受控空指针，错误地返回通用 500；应明确返回业务认证码 601，让客户端只执行一次受限刷新。

`auth-center` 当前 Session 建立、同用户复用和必要时轮换的源码行为正确，本次不修改。

原命令仍访问远程运行环境。认证服务能识别当前 SESSION，而远程 ERP 链路不能识别同一会话，说明剩余问题位于目标运行态的业务路由/实例/部署一致性边界。现有本地证据不足以在未部署、未读取目标配置的情况下进一步断言是 Cookie 请求头转发、混合版本实例还是运行时 Session 配置覆盖；不得把它描述为已解决或继续猜测性改代码。
