## 发布目标

将当前工作区已经完成本地 V3 验证的两项变更提交到 `origin/1.0.0`，并通过维护标签发布 npm `1.1.4`：

1. 统一透传 `find`、`describe` 与 `serve` 远端路由的实际 HTTP response body，移除 CLI envelope、候选裁剪、重排、派生字段与固定错误替换。
2. 修复长期 Token 会话续期：保留登录材料，安全持久化短期 Access Token，跨进程复用，并在缺失、到期或 401/601 时按契约换取和单次重试。

## 发布边界

- 只更新 npm `maintenance-1`；`latest` 必须继续保持发布前版本 `0.1.59`。
- 不使用只支持 `master`/`latest` 的根目录自动发布脚本；维护线通过精确版本提交和 `maintenance-1-v1.1.4` 标签触发既有 Release workflow。
- 不强推、不改写历史、不覆盖远端前进提交，不读取本机认证缓存，不执行真实登录或业务接口请求。
- 不记录或提交真实账号、Token、Cookie、Authorization 头、生产响应正文或其他敏感证据。
- CLI 发布不代表认证中心、网关或下游应用已经部署或完成真实环境联调。

## 验收标准

1. 工作区全部差异可归属到上述两项任务及本发布审计，无无关文件、占位实现或敏感信息。
2. frozen install、全仓测试、14 包构建、发布守卫、CLI/Skill smoke 与差异检查通过。
3. 功能提交和版本提交分别普通推送到 `origin/1.0.0`，对应分支 CI 成功后才进入下一阶段。
4. `packages/cli/package.json` 精确更新为 `1.1.4`，维护标签唯一且指向版本提交。
5. Release workflow 成功，npm 官方源可查询精确版本；`maintenance-1=1.1.4`，`latest=0.1.59`。
6. 从 npm 官方源隔离执行的版本、关键帮助与主/global Skill 验证通过。
7. 发布完成后回填两个关联任务、发布任务、项目记忆及审计索引，最终工作区干净且本地分支与远端一致。

## 风险与回滚

- 远端响应透传属于公共输出契约变更，下游若依赖旧包装或本地候选派生字段，需要同步迁移。
- Access Token 落盘扩大了认证缓存敏感度，必须保持当前用户权限、严格字段校验、到期禁用及不输出边界。
- 分支 CI 失败时停止后续版本或标签动作；Release 失败时保留唯一标签和作业证据，按根因修复后重跑，不创建同版本替代内容。
- npm 版本不可覆盖；若已发布版本存在严重缺陷，使用更高补丁版本修复。
