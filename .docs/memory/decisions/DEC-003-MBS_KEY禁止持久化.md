# DEC-003：MBS_KEY 禁止持久化

- 状态：有效规则，CLI 实现已随 npm `1.0.6` 发布并完成官方源命令核验，待真实联调
- 日期：2026-09-02
- 决策范围：MBS CLI 登录、刷新、凭据存储，以及依赖 MBS CLI 的服务端应用

## 背景

`MBS_KEY` 长期有效，并可解析账号密码材料，其安全等级高于普通短期会话 Cookie。现有 CLI 登录流程会捕获并持久化该值，刷新流程也依赖已保存的值。这会把一次浏览器登录扩大为长期凭据泄露风险。

浏览器完成 MBS 登录并获得 Cookie，不要求调用方解析或保存 `MBS_KEY`：调用方可以等待登录响应完成，再从隔离的浏览器上下文读取服务端签发的 Cookie。

## 决策

1. 所有 MBS CLI、报表服务及其前后端均不得捕获、存储、转发或记录 `MBS_KEY`。
2. 登录实现只允许等待认证完成并读取短期 Cookie；不得从请求或响应中解析 `MBS_KEY`。
3. 自动刷新不得依赖 `MBS_KEY`。Cookie 到期后重新进行用户授权，或使用 MBS 后端正式提供的服务身份/一次性授权码机制。
4. Docker 和编排平台的 Secret 也不是 `MBS_KEY` 的允许存储位置。
5. 既有本地 `MBS_KEY` 只允许在明确授权后按已知位置执行删除式清理；不得读取、解密、输出或迁移其值。本轮已取得授权并实现首次认证操作时的删除式清理。

## 影响

- CLI 的 `login`、凭据存储、`whoami` 和 `refresh` 在本任务中完成 SESSION-only 本地整改；其中“自动刷新能力不再提供”的实现影响已由后续 DEC-004 部分修正，MBS_KEY 禁令不变。
- 无浏览器的服务端不能通过保存用户 `MBS_KEY` 获得无人值守登录能力。
- 多用户报表系统需要建立用户浏览器与服务端会话之间的安全授权交接；共享定时报表则需要 MBS 后端提供受限服务身份。
- 在正式机制具备前，短期 Cookie 的人工注入只能作为经过明确批准的临时运维方案，不能成为默认设计。

## 依据

- 用户于 2026-09-02 明确确认：`MBS_KEY` 禁止保存到本地，属于长期凭据，并可解析账号密码材料。
- 本地最小验证确认：不捕获 `MBS_KEY` 不影响浏览器上下文接收 MBS 登录 Cookie。

## 后续演进

- 2026-09-03：认证中心提供正式登录型 Refresh Cookie 与 `/auth/token/exchange/compat-session` 后，DEC-004 补充了允许缓存 `AUTH_REFRESH`、Access Token 仅内存的边界。本文关于 `MBS_KEY` 的禁令完整保留；“CLI 自动刷新能力不再提供”这一实现影响被部分修正为“不使用 MBS_KEY、只使用正式 Refresh Cookie 刷新”。
