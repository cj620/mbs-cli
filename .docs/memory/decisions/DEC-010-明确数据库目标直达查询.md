# DEC-010 明确数据库目标直达查询

## 背景

统一语义发现最初面向“用户只描述业务目标”的场景，用于在 workflow、API 和 table 之间发现目标。用户已经提供完整只读 SQL 或精确物理表身份时，目标本身已经确定；继续调用 `mbs find` 不会增加必要信息，反而增加召回依赖、延迟和偏离用户明确目标的可能。

数据库命令仍需要 `host/database/schema`、权限过滤与 SQL 安检，因此“跳过语义发现”不能解释为直接信任表名或绕过数据库元数据与鉴权。

## 决策

- 完整、可执行的只读 SQL 跳过 `mbs find`，从 `mbs database my-tables` 开始解析并验证其物理表、数据源和权限，满足现有查询规则后执行 `mbs database query`。
- 精确物理 `tableName` 或完整 database/schema/table 身份跳过 `mbs find`，通过 `my-tables` 唯一匹配后执行 `show-create-table → query`。
- 业务别名、用途描述、不唯一名称和普通自然语言目标继续使用 `mbs find`；首次召回仍不根据模块关键词预判 `--domain`。
- 明确目标在 `my-tables` 中零匹配或多匹配时暂停并最小化消歧，不回退语义召回、不按相似度自动换表、不猜测数据源。
- 直达路径不改变后端二次鉴权、SQL 安检、权限改写、行数限制、资源熔断、响应透传和只读边界。

## 备选方案与权衡

- **所有业务查询继续 find-first**：规则简单，但对已明确目标产生无意义召回和误路由风险，不采用。
- **明确表名直接 query，不执行 my-tables**：调用最少，但缺少权威数据源和权限确认，且 `database query` 必须使用 `host/database`，禁止采用。
- **my-tables 未命中时回退 find**：可能发现相似表，但会把明确目标静默替换成另一对象，禁止采用。
- **所有数据库意图都先 my-tables**：可以减少语义依赖，但业务别名和跨 API/workflow 目标仍需统一排序与权限过滤，不采用。

## 后果与约束

- find-first 的适用范围从“所有业务查询”收窄为“目标未知的业务查询”；接口发现本身仍必须通过 `mbs find`。
- `my-tables` 是远端权限与数据源权威入口，不是本地表索引降级。
- SQL 引用多个物理表时，必须全部唯一匹配并属于可执行的同一数据源；无法确定时暂停。
- 用户提供的 SQL 表达明确查询意图，不应无理由改写指标、筛选、分组和排序；现有显式列、结果限制和只读规则仍优先。
- 本决策没有修改 CLI/后端契约，也不代表真实 MBS 数据库链路已经验收或发布。
