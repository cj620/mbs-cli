# DEC-008：认证失败保留与 Access 持久化

- 状态：已批准并随 npm `maintenance-1=1.1.4` 发布；真实认证联调未执行
- 日期：2026-09-08
- 决策范围：MBS CLI 认证缓存、长期凭据交换、Access Token 生命周期和业务请求认证恢复
- 来源任务：`20260908-[BUG]修复长期Token会话续期`

## 背景

当前 DEC-004 要求 Access Token 仅保存在当前进程内，并在部分认证或持久化失败时清除完整本地认证。
真实使用中，管理型 `LongToken` 登录后的新 CLI 进程只携带 `SESSION`；陈旧 Session 若被服务端返回为
403，不会触发既有的 401/601 刷新路径。重新登录更新 Session 后恢复，说明当前进程边界和失败清理
策略不能满足长期登录的可恢复性目标。

## 决策

1. 当前认证缓存允许保存严格校验的短期 Access Token 与绝对到期时间；缓存文件继续限制为当前用户可读写。
2. 有效磁盘 Access Token 可以作为普通业务请求的 Bearer；缺失或到期且存在受支持长期凭据时，通过 compat-session 申请并保存新 Access Token。
3. HTTP 401 与业务码 401/601 继续触发最多一次长期凭据交换和一次业务重试；403 继续表达权限拒绝，不做通用刷新。
4. 认证拒绝、交换失败、网络失败、响应非法和缓存写入失败均不得主动清空当前认证缓存。只有显式 `mbs logout` 或开始新的 `mbs login` 可以清空当前登录材料。
5. 最终业务错误继续原样输出后端 response body；Access Token、长期凭据、Cookie 和用户敏感信息不得进入输出、日志、错误、参数、环境变量、遥测或文档。
6. `MBS_KEY` 禁令、登录型 `AUTH_REFRESH` 与管理型 `LongToken` 互斥、长期凭据只发认证中心等 DEC-003/DEC-004 边界保持有效。

## 已确认重启语义

用户选择方案 A：电脑重启或终端会话变化后，磁盘 Access Token 仍未到期时直接复用；缺失或到期时才通过长期凭据重新申请。

## 权衡与后果

- 优点：短期 Token 可以跨 CLI 进程使用，长期登录不再依赖新鲜 Session；401/601 具备自动恢复路径。
- 代价：磁盘泄露面增加，必须依赖当前用户文件权限、短有效期、严格校验和全链路禁止输出。
- 保留失败状态便于网络恢复后重试，但服务端已撤销的长期凭据仍会留在本机，直到用户显式退出或重新登录。
- 不刷新通用 403 可保持权限语义，但服务端把认证过期错误错误映射为 403 时仍只能展示原始拒绝；请求前主动准备 Access 用于减少该触发面。

## 替代关系

- 部分替代 DEC-004 第 4 点“Access Token 仅进程内存”。
- 部分替代 DEC-004 第 5 点“认证拒绝或落盘不确定时清除本地认证”。
- 不替代 DEC-003，也不替代 DEC-004 关于长期凭据互斥、发送范围、SESSION-only 兼容和显式重新登录清理的其他规则。
- npm `maintenance-1=1.1.4` 已按本决策发布并完成官方源核验；`1.1.3` 及更早版本仍遵循 DEC-004 的历史行为。真实长期凭据与目标网关链路仍未联调。

## 验证要求

- 缓存合法、非法、过期、不完整、旧版本和文件权限测试。
- 管理型 LongToken 初登、两类长期凭据刷新和失败保留测试。
- 首发磁盘 Bearer、401/601 唯一刷新、连续失败、403 不刷新和后端 body 透传测试。
- login/logout 唯一清理路径静态检查与全仓 V3 回归。
- 敏感信息扫描和人工差异审查；不使用真实凭据。
